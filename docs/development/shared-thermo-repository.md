# 公共组分物性内核的仓库管理

本文确定 Guoqing Han 各模拟平台共用的组分物性内核的源码、验证和发布规则。算法以 `cupbhan/neqsim` 为唯一维护主仓库，持续接收 `equinor/neqsim` 更新；各产品使用具有明确版本和来源的发行包。本文是仓库维护规范，不代表任何新模型已通过现场验证。

## 仓库职责

| 仓库 | 职责 |
| --- | --- |
| `cupbhan/neqsim` | 官方算法及个人改进、模型资源、数值回归、现有 MCP 模块和内核发行包 |
| 拟建 `thermo-platform` | 独立流体管理、公共接口、客户端 SDK、PVT 表管理与插值；依赖内核发行版 |
| T2WELL、热井筒、oilfield-calc-platform | 模拟任务、界面和领域业务；不复制修改物性内核 |

公共服务仓库是后续交付项，本轮先完成内核整合和可追溯的候选构建。黑油模型将作为公共服务的另一种计算后端，保留自身模型定义和验证规则。

## 主线与官方更新

标准远端名为 `origin = cupbhan/neqsim`、`upstream = equinor/neqsim`。已有主分支继续使用 `master`，避免为命名调整改变历史。

| 引用 | 用途 |
| --- | --- |
| `upstream/master` | 官方代码跟踪引用，不直接加入个人改动 |
| `master` | 增强版主线，保留官方和个人改动的提交历史 |
| `feature/*` | 独立算法或功能开发 |
| `sync/*` | 官方版本升级的合并、冲突处理和回归 |
| `integration/*` | 多个已有分支的阶段性整合 |
| `release/*` | 有实际维护需要的旧发行版修复 |

官方更新先进入 `sync` 分支，完成源代码合并、数值比较和发行包验证后再合入主线。共享主线不强制推送，不通过重写历史消除个人补丁。每项个人改进记录目的、原始提交、对应测试、模型适用范围和上游接收情况。已由官方吸收的实现经对比后撤去重复补丁。

定期检查上游可以自动化；产品升级必须依赖通过检查的固定发行版。一次内核整合与一次官方大幅升级分开进行，便于定位数值变化。

## 版本与构建产物

增强版版本采用 `官方版本-cupbhan.序号`，候选版追加 `-rc.序号`。原有官方标签保持原义，个人发行标签使用 `cupbhan-v` 前缀。不能把同一版本号重新指向不同 JAR。

每个发行目录包含核心 library JAR 及其依赖 POM、核心源码 JAR、可独立运行的 MCP runner JAR、SHA256 清单、来源清单、许可证和验证报告。来源清单至少包括：增强版版本、官方基线提交、增强版源码提交、工作树状态、构建工具版本、产物路径和摘要、实际执行的验证范围及结果。核心 library 需要按 POM 加载依赖，runner 可以独立启动。

候选构建也必须从干净提交生成。构建后的来源清单与 JAR 一起分发；计算包不能仅凭文件名认定版本。MCP 依赖本次构建的核心 library，避免误用本机旧 Maven 缓存或把 shaded 核心再次装入 runner。

初期以版本目录交付候选包。对外发布 Maven 包前配置个人发布坐标，例如 `io.github.cupbhan`，并验证生成的 POM；不得沿用官方坐标向公共仓库发布增强包。尚未配置个人 Maven 发布时，不宣称该发布渠道已经可用。

本 fork 的继承发布工作流限制为只在官方仓库运行，个人候选由独立的 `shared_thermo_candidate.yml` 构建和保存附件。该流程不发布 Maven 包或 GitHub Release；默认 CI 候选号包含运行 ID，避免不同提交共用固定的候选号。

## 验证规则

| 检查层次 | 内容 |
| --- | --- |
| 源代码 | 核心保持 Java 8 源码兼容，默认编译目标 Java 17；MCP 使用 Java 21；执行 Spotless |
| 算法回归 | 闪蒸收敛、组分守恒、相分率、逸度残差、相识别和已保存的失败工况 |
| 模型回归 | 两烃相与含水三相的定义、相包络、重油多介质、CPA 与电解质 CPA 的区别 |
| 接口回归 | MCP 工具名称、参数、返回结构、错误处理；用实际发行 JAR 调用 |
| 参考对标 | 冻结的 PVTsim 输入、输出和容差；完整商业软件重算单独记录 |
| 产品接入 | 各平台分别进行现有用例回归，记录锁定版本和回退版本 |

编译成功、求解器返回成功、与参考软件一致、具备工程适用性是不同结论，应分别记录。升级后不能通过扩大容差或重写参考值隐藏回归。测试选择和跳过项写入报告；局部回归通过不能表述为全仓测试通过。

## 模型和结果的可追溯性

引擎版本、接口版本和流体对象修订号分别管理。流体对象包含组分及其计量基准、重端表征、EOS、混合规则、相互作用参数、校准信息、适用范围和成熟度。用户自建流体不因内核升级而被静默重写。

每份结果和 PVT 表记录引擎版本、计算包摘要、流体 ID 与修订号、输入摘要、单位、计算条件和插值规则。模型、参数或内核变化后重新判定缓存有效性；超出表格定义域不能静默外推。

## 历史资料整理

原有 `neqsim-sagd` 和快照目录完整保留于 `.local-archive/20261002/`，并记录提交和搬迁前后的文件摘要。Python 包装层纳入 `bindings/python/`。逐项迁移独有代码，不以覆盖目录代替合并。研究快照里的 `target/classes`、源码和旧 JAR 可能不同步，需要分别取证。

大型研究报告和原始扫描保留在归档中；仓库内维护来源索引、模型限制及便于自动执行的最小回归数据。商业软件历史结果与本次重算结果明确区分。实验代码只有在依赖、正确性和适用范围完成评估后才进入公共接口。

## 产品接入顺序

首先整合内核并生成候选包，然后使用现有热井筒客户端验证真实协议，再切换该产品的锁定依赖。T2WELL 和其他平台随后分别接入。最终逐步提取公共服务与 SDK，形成独立于模拟任务的流体管理功能。

开发模式允许显式指定本地候选包；默认运行不应依赖相邻源码目录的 `target`。所有切换保留旧版本及其回退路径。
